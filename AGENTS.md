# Agent guide

Friends-based Appalachian Trail fitness game for a hiking group. Static site on GitHub Pages (https://atfitnesstracker.abbydavid.com, repo `revDWD/oregon-trail-dle`) + Supabase project `eojzvyyhzdapwgsrtyne` (anonymous Auth, Postgres, RLS). Read `docs/architecture.md` (design) and `docs/review-and-roadmap.md` (Phase 2, 3 and 8 decisions and roadmap) first.

## Product context
- Purpose: motivation, accountability, friendly competition and community. Real exercise becomes trail miles. One **expedition** (the whole group) progresses together along the Appalachian Trail, northbound. Sprint motto (Phase 8): "less clutter, more personality". Never add Donner Party comparisons (owner request). Badge art may be playfully Oregon Trail-inspired.
- The organizer (Kevin) posts **Trail Dispatches**: encouragement, stories, milestone notes. These are the latest/pinned card on the Trail page plus the archive at Camp. Organizers are rows in `at_organizers`, added only via the SQL editor (see `docs/deployment.md`).
- **Hikers (Phase 8):** `at_hikers` is the official roster (David, Kevin; add/retire via SQL, see README). Every activity is logged *for a hiker* (required dropdown on Log Activity; the last choice is the `at.hiker` localStorage preference). There is **no invite code or join step** (removed 20261105: "select name → log activity → everything updates"); any signed-in device can log for any active hiker and read roster aggregates (`at_expedition_hikers`, `at_expedition_marks`). Each device still owns, and alone can edit/delete, its own rows. Activities without a hiker don't count toward the expedition; History asks to assign them (old rows stay editable while their date is unchanged, in both JS and SQL).
- **Expedition progress** = sum of hikers' credited miles (`expeditionTotals` in `engine/hikers.js`), northbound. Badges, milestones, the trail register and the per-hiker timeline are pure functions in `engine/hikers.js`; badge earn dates come from server-computed marks (who crossed each group/personal mile mark, and when). Badge art is original 12×12 pixel sprites in `ui/badge-art.js`.
- Trail tab: the map card holds **Journey progress** (regions as parents, landmarks as children: ✓ passed, ➜ next, ○ ahead) from `journeyProgress()` in `engine/progress.js`; there is no separate Landmarks card. Locked badges are silhouettes with no title or description until earned (discovery); the next-badge hint does not name the badge.
- Tabs (5): Trail, Log Activity, Camp, Wildlife Spotting, History (archive, last). **There is no Profile, Crew or Badges tab** (Profile removed in Phase 2, Crew in Phase 3, Badges moved into Camp per hiker in Phase 8). Old bookmarks are aliases in `app.js`: `#/hunt` opens Wildlife Spotting; `#/crew`, `#/badges` and `#/hikers` open Camp focused on "The hikers". Unknown routes fall back to Trail. The device ID lives in History > "About this device".
- **Camp** is the primary hub: the pixel SVG scene (driven by `engine/camp.js`: expedition miles, section scenery, seasonal weather, hikers, photo board) follows the device clock automatically (morning 5–9, day 9–17, evening 17–21, night 21–5; no buttons), then "The hikers" (picker + per-hiker panel; tapping a hiker in the scene selects them), the trail register and the dispatch archive. Crew features (`at_challenges`) are no longer in the UI; the tables and RPCs remain (dispatches can still be crew-only). The bear-bag line shows one bag per hiker at camp.
- **Wildlife Spotting** is the original Oregon Trail DLE hunt (tag `oregon-trail-final`, `assets/js/hunt-game.js`) restored and re-themed: same 30 s / 12 frames / 4-frame "film wind" / 1.1 s winding / startle / herd / pop-up pacing and the same pixel renderer, with a camera viewfinder, AT species and per-section habitats. `engine/expedition.js` holds the rules (pure, injectable RNG), `engine/expedition-themes.js` is data only (`wildlife`: species with sprites and behaviour, habitats keyed by region `scene`, words), and `ui/expedition-view.js` is the canvas, input and sound. Future AT activities (birding, foraging, scavenger hunts, clean-up) should be **new theme objects**, not new engines. Rounds auto-save to the photo board (pinned to the chosen hiker) when they score; empty rounds are not saved. Results **never award trail miles**. Old `hunt` rows in `at_expedition_runs` are simply ignored.

## Rules
- No build step; native ES modules; no runtime npm dependencies and no third-party CDN scripts. `@supabase/supabase-js` is vendored (update its checksum in `assets/vendor/supabase-js/README.md` when upgrading).
- There is no login UI by design: `auth.ensureSession()` uses Supabase anonymous sign-in. Do not add email/password flows unless asked.
- Never commit secrets. Only the public project URL and publishable key belong in `assets/js/at/config.js`. Never use a service-role/secret key in the browser.
- Supabase is the source of truth. `localStorage` may only hold harmless preferences: the selected challenge and the last hiker (`CHALLENGE_KEY`, `HIKER_KEY`; test-enforced). Other UI state (map zoom, selected hiker) stays in memory. All Supabase calls live in `assets/js/at/data/layer.js`.
- Credited miles and conversion factors are computed by the database trigger; the client never sets `user_id`, `credited_miles`, `conversion_factor`, `created_by` or `played_on`. Keep `engine/activities.js` rules in sync with the SQL (tests enforce this).
- Any schema change goes in a **new** idempotent migration (never edit an applied one) and must pass `bash supabase/tests/run-rls-tests.sh`, which applies every migration in order twice. The owner applies migrations by pasting them into the Supabase SQL Editor, so always give them the SQL inline. Security failures are blocking bugs.
- Render text with `textContent`/the `h()`/`svg()` helpers only: no `innerHTML` (test-enforced). Rich text goes through `engine/markdown.js` → `ui/markdown-view.js` (https links only).
- Trail data stays in `assets/js/at/trail/` (data only); logic stays in `engine/` (pure, DOM-free); `ui/map.js` keeps its view maths pure and exported for tests.
- Every view has exactly one `h1` with `data-focus` (test-enforced). The app re-renders the whole view on changes. A running Wildlife Spotting round must be stopped on re-render (`game.stop()` in `render()`); its keyboard listeners are on `document` while a round runs and are removed in `stop()`. The 60 s background refresh (`loadExpedition(true)`) only re-renders Trail/Camp when the data changed and nobody is typing (`typing()` in `app.js`); Camp also redraws when the time of day changes. One-time messages are `state.flash = { route, text }`, shown only on that page.
- Keep the game encouraging: no streak loss messaging, no rewards that scale with speed or daily volume, per-activity caps stay, minigames never add miles and are capped at 10 runs a day.
- Accessibility is required: keyboard use, visible focus, 44px targets, labelled fields, `aria-live` status, reduced motion (CSS animations off; the game runs slower), WCAG AA contrast. Anything drawn (map, camp, canvas) must also be available as text.
- `assets/js/at/ui/us-states.js` is a generated single-line file: do not view or edit it.
- Use original artwork only (no ATC logos, blazes or photos). Trail facts are approximate; see `docs/trail-data-sources.md`.

## Testing
`npm test` runs everything (Node test runner). The RLS suite needs PostgreSQL binaries and is skipped with a notice otherwise; CI installs them. Add tests with every feature. For visual checks, serve with `python3 -m http.server 8000` and use a 375px viewport. Supabase may be unreachable in sandboxes, in which case render views with synthetic state.

## Fail-soft
The app must keep working if a migration hasn't been applied yet: `loadCamp()` swallows dispatch errors, and only a *missing RPC* (`isMissingFunction`: PGRST202/42883) sets `state.expeditionUnavailable`, which hides the hiker field and takes progress from this device's `at_my_summary`. Other errors (timeouts, expired session, network) set `expeditionError` and keep the previous roster state, so a device is never dropped to the hiker-less form. Background redraws wait while focus is on a control in the page (`busy()`), so keyboard and screen-reader users keep their place.
